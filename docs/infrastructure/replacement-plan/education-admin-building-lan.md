# ⑧教育管理棟 LAN の実態

⑧教育管理棟（通称「管理棟」「大学院棟」）は不動坂南側のグループ3に属する神戸電子専門学校の建物である。配置図には「大学院」と記載されているが、KIC（神戸情報大学院大学）が入居しているのは⑩教育研究棟/学生会館であり、⑧ではない（`upstream-connectivity.md` の校舎配置図を参照）。

建物全体が `192.168.0.0/16` の1つのL2セグメントで、DHCPサーバ10台が同じセグメント上で競合している。利用者への影響が最も大きいのはこのDHCP競合で、再接続のたびにNAKによる取得失敗と、IPアドレス・出口回線の変更が起きている。

## 根拠データと観測範囲

| データ | 期間 | 内容 |
|--------|------|------|
| パケットキャプチャ | 2026-10-21 21:59〜11-06 16:34 | 建物LANの有線1ポートで受動観測（観測側のNICにIPアドレスを持たせず、自局からは送信しない）。2,353万フレーム、4.13GB、送信元MAC 1,387個 |
| ゲートウェイのSNMPカウンタ | 2026-09-18〜11-06 | RTX830 2台のインターフェースカウンタ・CPU・メモリを30秒間隔で取得。RTX1210は取得対象外 |
| Wi-Fi端末からの機器調査 | 2026-05-08 | DHCP OFFERの全数採取、ARPスキャン、traceroute、SNMPによる機種特定 |

観測位置による制約:

- 1ポートに届くのはブロードキャスト、マルチキャスト、宛先不明でフラッディングされたユニキャストだけである。端末宛てのユニキャスト（DHCPのOFFER/ACKの多く）は、ブロードキャストフラグ付きのものを除いて見えない。DHCP NAKはブロードキャストなので全数が見える
- 平日9〜15時のブロードキャストは観測ポートで中央値31fps、RTX830 2台のLAN側ブロードキャスト受信はp95で31ppsで、ルーターと同じブロードキャストドメインを観測している
- キャプチャには2026-10-29 15:03からの約96時間の欠測があり、SNMPにも数件の欠測がある。いずれも観測側の都合によるもので、建物側の停止ではない。キャプチャの全期間を通じて、建物全体のL2が止まった区間はない（STPのルートBPDUが2秒間隔で届き続けている）
- 無線側（APの接続台数、無線時間の使用率）のデータはない

### 出口回線

| ルーター | 機種 | 回線 |
|---------|------|------|
| `192.168.0.252` | YAMAHA RTX830 | NURO |
| `192.168.0.253` | YAMAHA RTX830 | NURO（.252 とは別回線） |
| `192.168.0.254` | YAMAHA RTX1210 | ぷらら |

- 回線の振り分けは、どのDHCPサーバからリースを受けたかで決まる（端末が受け取るデフォルトゲートウェイ＝出口回線）
- RTX830 2台の負荷は低い。CPUは最大21%、メモリ30〜49%、インターフェースエラー0、破棄はほぼ0
- WAN側受信はp95で72Mbps、p99で約200Mbps、最大542Mbps（.252、2026-10-05 09:59）
- ルーター3台とも管理プロトコル（Telnet、HTTP、SNMPv1）が建物LANの全端末から到達できる
- RTX1210のファームウェアは2019年版（Rev.14.01系）のまま
- .252 と .253 は別筐体で、VRRP等の冗長構成ではなく単に並列に置かれている

## 問題点（利用者への影響が大きい順）

### 1. DHCPサーバ10台の競合

端末が再接続時に以前のIPアドレスを要求する（INIT-REBOOT）と、そのアドレスを持たないサーバ群がNAKを返す。

| 指標 | 値 |
|------|-----|
| INIT-REBOOTのREQUEST（トランザクションID単位） | 30,502 |
| うちNAKを受けたもの | 30,441（99.8%）。1回の要求に対するNAKは4〜9件、最頻値は9件（所有者以外の全サーバ） |
| NAK後15秒以内にDISCOVERからやり直したもの | 23,842（78%） |
| やり直しが起きた端末 | 915（DHCPを送信した1,211 MACの76%） |
| DHCP NAKの総数 | 219,271 |

- 所有者のサーバのACKは多くが端末宛てのユニキャストで、この位置からは見えない。ただしNAKを受けた要求の78%で15秒以内にDISCOVERが続いており、端末は他サーバのNAKに従ってリースを捨てていると考えられる。その後のDISCOVERでは最も速く応答したサーバのリースを受けるため、プールとゲートウェイ（出口回線）が変わる
- ブロードキャストフラグを立ててACKを受けた端末だけは、リースの移り変わりを追跡できる（1,211 MACの一部であり、全体を代表するものではない）。追跡できた154台のうち129台が複数のプールからリースを受けており、25台は10プールすべてを渡り歩いている。プールの変更は2,560回、ゲートウェイの変更は1,882回。出口回線が変わると送信元のグローバルIPも変わるため、通信中のセッションは切れる
- 提示されたアドレスが既に使用中だったことを示すDECLINEは916件（653アドレス、191 MAC）で、全プールに分散している（RTX1210のプールが最多の216件）

### 2. 端末1台のARPスキャンが建物全体に波及する（2026-10-22）

- 10:30から端末1台（Intel NIC）が `/16` 全体（65,533アドレス）にARP要求を送り、各アドレスに約1秒間隔で6〜12回再送している。合計約89万件
- ピークは10:44〜10:50で毎秒約3,700件。同時刻にRTX830 2台のLAN側でもブロードキャスト受信が2,748pps / 2,474pps（1分平均）に達している
- 同じ時間帯（10:44:30〜10:49:56）、2台目のNetgearがルートのBPDUを受け取れなくなり、自分がルートだと主張しては戻る動作を約1秒ごとに繰り返している。観測ポートにはルートのBPDUが2秒間隔で届き続けており、原因はそのスイッチのCPU負荷か、途中の家庭向けスイッチでの取りこぼしのどちらかである
- `/16` の1セグメントであるため、1台の端末のスキャンが建物内の全端末・全APに届く。APは受け取ったブロードキャストを無線へ送り直すので、無線時間の大半を消費しうる（無線側のデータがないため影響量は未確定）

### 3. 常時流れる全館向け通信

- 平日日中の中央値73fps、p95 154fpsのブロードキャスト・マルチキャストが、建物内の全ポート・全SSIDに流れている
- 量の大半はmDNS（個人端末・家電の相互探索）、ARP、家庭向けスイッチのループ検知フレームで、いずれも1セグメントの範囲を狭めれば届く範囲も狭まる
- 少なくとも11台の家庭向けスイッチが同じL2にある。これらはVLANタグの扱いが機種依存で、マネージドスイッチの代わりにはならない

### 4. 宛先不明ユニキャストのフラッディング

- 合計394,666フレーム。端末間の通信が約31万件、ルーターから端末への通信が約8万件
- 最大のものは2026-11-06 14:57〜15:00の端末間HTTP/TLS通信（約26万件、最大毎秒約4,000件）で、宛先MACがスイッチのMACテーブルにないため全ポートに流れている
- ルーターから端末への約8万件は、ルーターのARPキャッシュに残る端末のMACがスイッチのMACテーブルから先に消えたときに起きる、典型的な非対称フラッディングと考えられる

### 5. ルーター2台の同時再起動（2026-10-29 09:03）

- RTX830 2台のカウンタが同じ時刻に同時にリセットされている。同時刻（09:03:20）に2台目のNetgearが再起動時（またはポートのリンク断時）と同じBPDUを出している
- 観測ポート側のリンクはこの間も途切れていない。ルーター側の機器が同じ電源系統を共有しているなど、共通の原因で同時に落ちた可能性がある
- 2026-05-08時点のSNMPでもルーター3台の稼働時間の差は100秒以内であり、同時再起動はこのとき限りのものではない

### SNMPの応答遅延

RTX830へのSNMP取得で、タイムアウトと再送（応答待ち5.2秒、10.2秒、15.2秒）が平日9〜15時にだけ発生する。日中に、観測点からルーターまでの経路、またはルーターのSNMP応答のいずれかでパケットが失われている。発生区間は特定できていない。

## IPv6マルチキャスト

- IPv6マルチキャストは全フレームの20.3%で、その73%はIPv6上のmDNSである
- RA（ルーター広告）は0件で、RS（ルーター要求）約8.7万件はすべて応答がない。NSは約63万件、MLDv2 Reportは1,185の送信元から約33万件
- 宛先の `33:33:xx:xx:xx:xx` は2,483種類で、ピークは毎秒約290フレーム
- アクセス層が全ポートに流す家庭向けスイッチであるため、L2MCテーブルの枯渇が起きているかは1ポートからは検証できず、この建物では問題の主因でもない。`deployment-strategy.md` のIPv6マルチキャストによる障害の推定は本館についてのものであり、この建物の結果では肯定も否定もできない

## 対処の方向

- **1つのL2に置くDHCPサーバを1台にする**。NAKの応酬とIP・出口の変更は、同じL2に複数のサーバがあることから生じる。WAPM-2133TR 7台のDHCPサーバ機能を無効にし、RTXのうち1台だけが配布すれば解消する。3回線の併用は、DHCPの競合ではなくルーター側の経路制御で行う
- **配布マスクを /24 に変えるだけでは解決しない**。ゲートウェイ（`192.168.0.25x`）が各プールの /24 の外になり、多くの端末で外に出られなくなる。複数サーバが同じL2で応答する構造も変わらない
- **セグメント分割にはマネージドスイッチが要る**。`/16` の1セグメントを解消し、VLANごとにDHCPサーバを1台とする。経路上の家庭向けスイッチの交換が前提になる
- STPを使う場合は、ルートにしたいスイッチのブリッジ優先度を明示的に下げる

## eduroam導入への影響

- **MACアドレスによる端末管理は成り立たない**。送信元MACの77%がランダム化されており、個人単位の認証（802.1X）が前提になる
- **eduroam SSIDは専用のVLANとDHCPスコープに分ける**。既存のL2にブリッジすると、上記のDHCP競合（NAK、IPと出口の変更）をそのまま引き継ぐ。VLANごとにDHCPサーバを1台に限定する
- **VLANを通すにはスイッチの交換が前提**。経路上の家庭向けアンマネージドスイッチ（11台以上）はVLANタグの通過が保証されない
- **VLANを分けても無線時間は共有される**。同じAPの既存SSIDに流れるブロードキャスト・マルチキャストは、eduroam SSIDと同じ無線時間を消費する。既存SSID側のセグメント分割（`/16` の1セグメントの解消）も合わせて必要
- **APの置き換え時はDHCPサーバ機能を無効にする**。WAPM-2133TRは802.1X（WPA2-Enterprise）とタグVLANに対応しているが、802.11k/v/rには対応していない
- APからRADIUSサーバへの経路が別途必要。この建物の出口はISP回線3本で、他棟との接続は確認されていない
